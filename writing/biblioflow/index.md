# BiblioFlow


BiblioFlow is concept-level work: a design for moving the [AI metascientist](/writing/ai-metascientist/) away from frontier-model orchestration and toward a local, governed bibliometric workflow system. It follows from the [Claude Projects workflow experiment](/tools/claude-projects-workflows/), which showed that project files can encode stages, gates, and methodological constraints, but also showed the limits of keeping too much analytical state inside a conversational environment.

The reason is not that frontier models are useless; I use them constantly. The reason is that they remain black boxes at the point where I most want the system to be inspectable: what task was performed, which rule was applied, which assumption entered the workflow, and why the system allowed the analysis to proceed.

The direction I want to explore is to replace one-prompt behaviour with well-scoped tasks. The Corpus Builder already points that way. Instead of asking a model to “build a corpus”, the workflow breaks the work into small stages: ingest the brief, probe seed publications, recommend a retrieval method, define the field, design the field structure, design the retrieval strategy, generate candidate queries, calibrate on counts and samples, review validation, request execution approval, retrieve the corpus, and release a documented package. Each stage has a narrow job; each gate requires human sign-off before the workflow can move on.

That structure matters because corpus building is where a lot of analytical authority enters the system, often before anyone has started “analysis” in the visible sense. Which seed papers count as central, whether a field is retrieved through Boolean terms or classifications, whether a broad FoR code is too coarse, which false friends get excluded, whether a missing sub-theme becomes a known limitation or a manual supplement: these are methodological decisions. I do not want them hidden inside a long prompt and a plausible answer. I want them surfaced, versioned, and available for inspection.

In the current Claude Projects version, the project context carries much of that structure. The Corpus Builder instructions define the stages and gates; the AI Metascientist prompt routes requests into workflows and applies governance rules. That works as a prototype, but it still leaves too much inside the conversational environment. BiblioFlow would pull that structure out into a system architecture: small task modules, explicit state, local model calls where the task is narrow enough, and BigQuery execution through an MCP layer rather than through a model improvising SQL.

The AI metascientist would change shape in that version. Instead of being a frontier-model project with instructions, it would become a semantic layer plus a governed execution layer. The semantic layer would describe the bibliometric world the system is allowed to reason over: publications, journals, researchers, organisations, funders, fields, grants, patents, policy documents, classifications, identifiers, counting levels, citation windows, normalisation rules, and the conditions under which each metric or workflow is valid. The BigQuery MCP would handle controlled access to the data: schema inspection, query execution, result retrieval, and logging. The model would not need to “know” bibliometrics in the broad, unstable sense; it would need to perform bounded tasks against a representation that tells it what the entities and rules are.

The local-model part is important, but only for the right jobs. I would not ask a small local model to invent a bibliometric method or decide whether a research evaluation question is valid. I would use it for constrained operations: classifying a user request against known workflow types, checking whether a proposed field definition matches approved scope, labelling validation samples against explicit inclusion criteria, detecting likely false positives, drafting a limitations note from recorded calibration results, or checking whether a report has declared the required caveats. Those are narrow tasks with visible inputs and assessable outputs. That is where local AI is useful.

The harder work is deciding what belongs in the semantic layer. For BiblioFlow, I would start with the corpus builder because it is the easiest place to see the workflow logic. The first version would encode the approved stages, gate states, artefact statuses, retrieval-method scorecards, false-friend checks, sampling rules, release-package requirements, and handoff format. Once that exists, the analytical workflows can consume a released corpus without rebuilding the field from scratch. WF0 becomes a reusable corpus object, not a conversational prelude.

The next layer would encode the research-intelligence workflows themselves. A field landscape workflow, a benchmarking workflow, an internal portfolio audit, an impact assessment, an integrity-signal screen, a collaboration longlist, a foresight workflow, a competitor-intelligence workflow: each one needs its own scoping rules, valid inputs, required caveats, metrics, chart constraints, and refusal conditions. The model can help the user move through those workflows, but the workflow decides what has to be asked, what can be defaulted, what must be refused, and what has to appear in the audit log.

What I want to test with BiblioFlow is whether this architecture can reduce dependence on frontier models without losing the conversational usefulness that made the AI metascientist worth exploring in the first place. The conversation should remain useful at the boundary: helping users express intent, clarify scope, and understand outputs. The analytical core should become less conversational, not more: explicit semantic layer, governed BigQuery execution, small model tasks, documented gates, and outputs that can be traced back to the decisions that produced them.
